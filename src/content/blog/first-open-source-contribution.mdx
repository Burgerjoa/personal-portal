오픈소스 기여라고 하면 뭔가 거창한 걸 떠올리게 된다.

유명한 라이브러리에 큰 기능을 추가한다거나, 복잡한 버그를 고친다거나, 전 세계 사람들이 쓰는 도구의 핵심 구조를 바꾼다거나.

그런데 내 첫 오픈소스 기여는 생각보다 더 생활감 있는 문제에서 시작됐다.

Obsidian 안에서 LLM 서비스를 어떻게든 써보려고 몸부림치던 중이었다.
노트는 Obsidian에 있고, 코드도 보고 싶고, 터미널도 쓰고 싶고, LLM CLI 도구도 연결하고 싶었다.

한마디로 Obsidian을 그냥 메모 앱이 아니라, 내 작업실이자 LLM 개발 환경처럼 쓰고 싶었다.

그러다가 Termy를 보게 됐다.

Termy는 Obsidian 안에서 터미널을 띄울 수 있게 해주는 플러그인이다. Obsidian 내부에서 터미널을 열고, Claude Code나 Codex CLI 같은 LLM 기반 CLI 도구를 연결할 수 있다면 꽤 괜찮은 흐름이 나올 것 같았다.

노트에 생각을 적고, 바로 옆에서 터미널을 열고, LLM에게 명령을 보내고, 결과를 다시 노트로 가져오는 식이다.

그런데 막상 써보니 문제가 있었다.

## 문제는 한글 공백이었다

처음에는 그냥 내가 뭘 잘못 설정한 줄 알았다.

영어 입력은 큰 문제가 없는데, Windows 환경에서 한글을 입력하면 공백 위치가 이상하게 밀렸다. 글자가 완전히 안 입력되는 것도 아니고, 터미널이 아예 멈추는 것도 아니었다.

그래서 더 애매했다.

예를 들면 이런 문장을 입력하려고 했다.

```text
저는 홍길동 입니다
```

그런데 실제로는 이런 식으로 들어갔다.

```text
저 는홍길 동입니다
```

단순히 보기 불편한 정도가 아니었다.

LLM CLI 안에서 프롬프트를 입력할 때 한글 공백이 깨지면 문장 자체가 어색해진다. 특히 한국어로 지시문을 길게 작성하거나, Obsidian에 정리해둔 내용을 터미널로 가져와서 LLM에게 넘기는 흐름에서는 이 문제가 꽤 치명적이었다.

처음에는 한글 입력기 문제인가 싶었다.
그다음에는 Obsidian 문제인가 싶었다.
조금 더 보니 Termy 내부의 터미널 입력 처리와 Windows 환경이 엮인 문제처럼 보였다.

## IME는 그냥 키보드 입력이 아니었다

한글 입력은 영어 입력처럼 키를 누르는 즉시 문자가 확정되는 구조가 아니다.

영어로 `a`를 누르면 보통 바로 `a`가 들어간다.
하지만 한글은 `ㅎ`, `ㅏ`, `ㄴ` 같은 자모가 조합되어 `한`이라는 글자가 만들어진다.

이 과정에는 조합 중인 상태가 있다.

예를 들어 사용자가 한글을 입력하는 동안 브라우저나 앱 입장에서는 대충 이런 흐름이 생긴다.

```text
compositionstart
compositionupdate
compositionupdate
compositionend
input
```

즉, 사용자가 키를 누를 때마다 바로 최종 텍스트가 들어가는 것이 아니라, IME가 조합 중인 텍스트를 관리하다가 어느 순간 확정한다.

문제는 이 조합 중인 상태에서 공백을 누를 때 생겼다.

한국어 문장을 입력할 때 공백은 단순히 빈 칸 하나가 아니다.
조합 중인 글자를 확정하면서 다음 단어로 넘어가는 신호이기도 하다.

그런데 터미널 입력 처리 쪽에서 이 공백 이벤트를 너무 먼저 가져가면, IME가 기대한 순서와 다르게 입력이 전달될 수 있다.

그래서 문장이 이런 식으로 깨지는 것이다.

```text
원래 기대한 흐름:
저는 + 공백 + 홍길동 + 공백 + 입니다

실제 깨진 흐름:
저 + 공백 + 는홍길 + 공백 + 동입니다
```

겉으로 보면 그냥 공백 위치가 이상한 버그지만, 안쪽에서는 IME 조합 상태와 터미널 입력 이벤트 처리 순서가 어긋난 문제에 가까웠다.

## Windows conpty와 win32 input mode

문제가 특히 Windows 환경에서 나타났던 이유도 있었다.

Windows 터미널 계열에서는 conpty라는 pseudo console 계층을 거친다.
Termy처럼 웹 기반 터미널 UI와 실제 셸을 연결하는 도구는 대체로 이런 구조를 가진다.

```text
Obsidian Plugin
→ Terminal UI
→ xterm.js
→ PTY Backend
→ Windows conpty
→ PowerShell
```

여기서 xterm.js는 브라우저나 Electron 환경에서 터미널 UI를 구현할 때 자주 쓰이는 라이브러리다. 사용자가 터미널 화면에 입력한 키를 받아서 실제 셸로 전달하고, 셸에서 나온 출력을 다시 화면에 그려준다.

그런데 Windows conpty 환경에서는 `win32-input-mode`라는 입력 처리 방식이 관여할 수 있다.

이 모드는 Windows 콘솔의 입력 이벤트를 더 직접적으로 처리하기 위한 방식에 가깝다. 일반적인 텍스트 입력이라면 문제가 없을 수 있지만, CJK IME처럼 조합 상태가 있는 입력과 만나면 이야기가 복잡해진다.

내가 겪은 문제는 대략 이런 쪽이었다.

```text
1. 사용자가 한글을 조합 중이다.
2. 아직 IME 내부에서는 글자가 완전히 확정되지 않았다.
3. 사용자가 공백을 누른다.
4. win32 input mode 쪽에서 공백 키 이벤트를 먼저 처리한다.
5. IME 조합 버퍼가 기대한 순서와 다르게 확정된다.
6. 결과적으로 단어 사이 공백 위치가 깨진다.
```

즉, 핵심은 “공백이 입력된다”가 아니라 “공백이 너무 이른 타이밍에 전달된다”였다.

## 해결 방향

해결은 생각보다 단순한 방향으로 잡았다.

CJK IME 입력이 활성화된 상태에서는 `win32-input-mode`가 우선되지 않도록 막고, 일반적인 텍스트 입력 파이프라인이 먼저 동작하도록 했다.

개념적으로는 이런 느낌이다.

```ts
if (isCjkImeActive) {
  win32InputModeEnabled = false;
}
```

물론 실제 수정은 이보다 맥락이 더 필요했다.

입력 이벤트가 들어오는 위치, 터미널 인스턴스가 생성되는 위치, IME 상태를 추적하는 방식, 스타일 레이어에서 조합 중인 텍스트가 어색하게 보이지 않도록 하는 부분까지 같이 봐야 했다.

중요한 건 “한글 입력 중에는 Windows의 특수 입력 모드보다 IME 조합 흐름을 우선시해야 한다”는 판단이었다.

이렇게 바꾸면 공백이 IME 조합 큐를 우회해서 먼저 들어가지 않고, xterm.js 쪽의 일반 텍스트 입력 흐름을 통해 더 자연스럽게 처리된다.

결과적으로 한글 문장을 입력할 때 공백이 단어 중간으로 튀는 문제가 사라졌다.

## 고친 것보다 설명하는 게 더 어려웠다

코드 수정 자체보다 더 어려웠던 건 PR 설명이었다.

혼자 쓰는 코드라면 “어쨌든 고쳤음” 하고 넘어갈 수 대만,
하지만 오픈소스에 PR을 보내려면 관리자가 문제를 이해할 수 있어야 한다.

그래서 설명에는 최소한 이런 내용이 필요했다.

```text
어떤 환경에서 문제가 발생했는가
어떤 입력을 했을 때 재현되는가
실제 결과와 기대 결과가 어떻게 다른가
원인을 어디로 판단했는가
어떤 방식으로 수정했는가
수정 후 어떤 동작을 확인했는가
```

내 입장에서는 “한글 공백이 이상하게 밀려요”였지만, 관리자의 입장에서는 이게 정말 프로젝트 문제인지, 특정 환경 문제인지, 수정이 다른 입력 처리에 영향을 주지는 않는지 판단해야 한다.

그래서 PR에는 Windows conpty/PowerShell 환경에서 CJK IME 조합 중 공백 문자가 먼저 전달되어 단어가 깨지는 문제라고 정리했다.

그리고 원인은 `win32-input-mode`가 활성화된 상태에서 conpty의 키 입력 변환과 IME 클라이언트 버퍼가 충돌하는 것으로 보았다.

해결책은 CJK IME 입력 중 `win32-input-mode`를 비활성화해 일반 텍스트 입력 파이프라인이 우선되도록 하는 것이었다.

작은 수정이었지만, 문제를 설명하기 위해서는 꽤 많은 맥락이 필요했다.

## merge

PR은 결국 원본 저장소에 merge됐다.

처음에는 그냥 내가 Obsidian 안에서 LLM을 좀 더 편하게 쓰고 싶어서 시작한 일이었다.
그런데 그 과정에서 터미널 플러그인의 한글 입력 문제를 발견했고, 코드를 읽고, 원인을 좁히고, 수정하고, 원본 프로젝트에 반영했다.

엄청 큰 기여는 아닐 수 있다.

하지만 내 입장에서는 꽤 의미 있는 첫 경험이었다.

내가 쓰는 도구에서 불편을 발견했다.
그 불편이 왜 생기는지 추적했다.
작은 수정으로 해결했다.
그리고 그 수정이 upstream에 들어갔다.

이 흐름을 한 번 경험했다는 게 중요했다.

## 오픈소스 생태계는 멀리 있지 않았다

이번 일을 겪고 나서 오픈소스 기여에 대한 생각이 조금 바뀌었다.

예전에는 오픈소스 기여라고 하면 내가 잘 모르는 거대한 생태계에 들어가서, 엄청난 실력을 가진 사람들 사이에 뭔가를 해야 하는 일처럼 느껴졌다.

그런데 실제로는 조금 달랐다.

내가 매일 쓰는 도구가 있다.
그 도구에서 내 환경에서만 잘 드러나는 문제가 있다.
특히 한국어, Windows, Obsidian, LLM CLI 같은 조합은 모든 사용자가 겪는 환경은 아닐 수 있다.

그렇다면 그 문제를 발견한 사람이 직접 고치는 것도 충분히 의미 있는 기여가 될 수 있다.

이번 문제도 그랬다.

영어만 쓰는 사용자라면 이 문제를 못 봤을 수도 있다.
macOS만 쓰는 사용자라면 재현하지 못했을 수도 있다.
Obsidian 안에서 LLM CLI를 연결하려고 하지 않았다면 애초에 마주치지 않았을 수도 있다.

내가 쓰는 언어, 내가 쓰는 운영체제, 내가 만들고 싶은 작업 흐름이 겹치면서 발견한 문제였다.

그래서 더 기억에 남는다.

## 남은 생각

이번 기여는 나에게 “오픈소스를 한다”는 말의 기준을 조금 낮춰줬다.

처음부터 큰 기능을 만들 필요는 없다.
유명한 프로젝트의 핵심 구조를 바꾸지 않아도 된다.
수많은 사용자를 한 번에 만족시키지 않아도 된다.

작은 불편을 그냥 넘기지 않는 것.
문제를 재현해보는 것.
코드를 읽고 원인을 좁혀보는 것.
수정한 내용을 다른 사람이 이해할 수 있게 설명하는 것.

그 정도의 일도 충분히 오픈소스 생태계에 참여하는 방식이 될 수 있었다.

그리고 개인적으로는 이 경험이 꽤 내 방향과도 맞았다.

나는 요즘 Obsidian, LLM, 터미널, 브라우저 확장, MCP 같은 도구들이 서로 연결되는 흐름에 관심이 많다.
단순히 하나의 앱을 쓰는 게 아니라, 내 작업 환경 전체를 하나의 개발자 워크플로우로 만들고 싶다.

이번 Termy 기여는 그 과정에서 나온 작은 부산물이었다.

하지만 동시에 내가 어떤 문제에 관심이 있는지도 보여준다.

개발자가 매일 쓰는 도구.
LLM을 활용하는 작업 흐름.
한국어 사용자 경험.
로컬 환경에서 돌아가는 생산성 도구.
그리고 그 사이에서 생기는 작지만 귀찮은 문제들.

앞으로도 이런 문제를 그냥 넘기지 않고 하나씩 고쳐보고 싶다.
